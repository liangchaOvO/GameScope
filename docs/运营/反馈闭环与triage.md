# 反馈闭环与每周 Triage（M2′）

## 渠道

| 渠道 | 用途 | 负责人 |
|------|------|------|
| GitHub Issues（bug / 指标模板贡献 / 功能建议 三模板） | 可复现问题与明确提案 | 创始人 |
| GitHub Discussions | 安装与一般讨论 | 创始人 |
| 用户群（微信群 / Discord，二选一起步） | 快速反馈与口碑；群公告固定附仓库链接与「报 bug 请走 Issue」指引 | 创始人 |

> 群内反馈的处理规则：能一句话答的答；超过三句的引导去 Issue；出现两次以上的同类问题必须建 Issue（哪怕自己复述）。

## 每周 Triage 流程（每周一，30 分钟）

1. 过一遍本周全部新 Issue，打标签：`bug` / `metric-template` / `enhancement` / `docs` / `wontfix`；
2. 每个 bug：确认可复现 → 标 `confirmed` 并记影响面（阻断/一般/边缘）；
3. 每个指标模板贡献：按五要素完整性初筛（定义/口径/健康区间出处/图表/教学卡片），缺出处的不合并；
4. 挑出「本周必修」≤3 项与「下周候选」≤5 项，写入 triage 报告；
5. 输出 `docs/运营/triage-YYYY-Www.md`（模板见下）。

### Triage 报告模板

```markdown
# Triage 第 N 周（YYYY-MM-DD ~ YYYY-MM-DD）
## 数字
新增 Issue X（bug X / 模板 X / 建议 X），关闭 X，净增 X；star X（+X）；clone/试用 X
## 本周必修
- [ ] #编号 一句话（影响面）
## 下周候选
- #编号 一句话
## 值得注意的反馈原话（脱敏）
- 「……」—— 来自 Issue #编号 / 用户群
## 指标模板贡献队列
- #编号 名称 → 状态（初筛通过 / 缺出处 / 需实测）
```

## 升级规则

- 数据泄露类反馈（哪怕疑似）→ 立即停相关端点并当日处理，不受周节奏限制；
- 门禁退化（评测脚本重跑 <24/30）→ 暂停新功能发布，先修回归。

## 用户群冷启动

1. 首批邀请：立项书 §3 的目标用户画像中的熟人开发者（5–10 人），逐一私信而非群发；
2. 群公告固定三条：仓库链接、Issue 指引、「本地部署处理商业数据」建议；
3. 每周在群内同步一次 triage 摘要（修复了什么、拒绝了什么、为什么）。
